sections:
  - id: hook
    heading: A more specific question than "is this obfuscated"
    body: >-
      Most work on obfuscated malware asks whether a sample has been obfuscated at all. ObfuScope asks a narrower, more useful question - given an obfuscated sample, can you fingerprint which specific obfuscation toolchain produced it? Different tools leave different structural fingerprints, and that fingerprint is itself a signal worth extracting.
    bullets:
      - Serving as a research assistant on the project, led by a Weber State CS professor.
      - Focus is toolchain attribution, not malware detection itself.
      - Submitted to ACM Transactions on Privacy and Security (TOPS) in 2026.
  - id: data
    heading: The dataset
    body: >-
      The analysis draws on a substantial and diverse set of obfuscated artifacts, spanning many distinct malware families and multiple obfuscation approaches - important for a model that has to generalize across obfuscators it wasn't trained on.
    bullets:
      - 4,121 obfuscated C artifacts drawn from 102 malware samples.
      - Samples span 90 distinct malware families and 11 transformation families (obfuscation types).
      - Diversity across both malware family and obfuscation type was deliberate - a model that only works within one family isn't actually solving the attribution problem.
  - id: features
    heading: A 61-feature static feature space
    body: >-
      Rather than relying on a single signal, the feature space spans seven distinct families of structural and statistical characteristics extracted directly from the obfuscated binaries.
    bullets:
      - Lexical, entropy, control-flow, literal, operator, API, and obfuscation-indicator feature families.
      - 61 features total, engineered specifically to capture how different obfuscation toolchains alter a binary's structure.
      - Static analysis only - no execution or dynamic instrumentation required.
  - id: evaluation
    heading: Three evaluation protocols, not one
    body: >-
      A model that performs well under one evaluation scheme can still be overfit to the specific families or obfuscators it was trained on. Three separate protocols test that directly, including an open-set scenario the model has never seen anything like.
    bullets:
      - Grouped cross-validation as the baseline evaluation.
      - Leave-malware-families-out, to test generalization across malware families the model wasn't trained on.
      - Leave-one-obfuscation-out (open-set), testing whether the model can recognize a genuinely novel obfuscation type as novel, rather than misclassifying it as one it knows.
  - id: results
    heading: Results
    body: >-
      An Extra-Trees classifier was the best-performing model across the evaluation suite, with strong results even under the hardest, open-set condition.
    bullets:
      - Extra-Trees classifier achieved 0.993 macro-F1 across grouped cross-validation.
      - 0.988 AUROC on the open-set novelty protocol - meaningfully strong performance at recognizing an obfuscation type the model never trained on.
      - Experiments run on HTCondor/DAGMan across the Open Science Pool's high-throughput computing infrastructure.
  - id: reflection
    heading: My role
    body: >-
      Joined as a research assistant once the core modeling work was done, with four specific responsibilities: verify the project actually holds up, then help make the paper better.
    bullets:
      - Reviewing and testing the project's code for completeness and reproducibility - checking that scripts run end to end, dependencies are documented, and results actually reproduce, then running the workflow directly on the Open Science Pool's HTCondor/DAGMan infrastructure.
      - Reading the full paper end to end and revising it for writing quality, technical accuracy, and logical flow, including sharpening how clearly it states the paper's actual contribution.
      - Conducting a literature review to identify related work using similar datasets, models, or evaluation methods, for the paper's related-work section and comparisons.
      - Reporting findings back with specific notes on code issues, unclear parts of the paper, and gaps in the related-work coverage.
